title: Knowledge packs
description: KnowledgePack and its entry types, the bundled default pack, JSON parsing and serialization, overlay merging.
---

A knowledge pack is JSON mapping "language-independent key → reading text and school attributes".
The core only judges facts; reading texts and the school-specific star attributes live here. For the
concept, the format and how to write an overlay, see the
[knowledge pack guide](/en/docs/guide/guides/knowledge-pack); the full field reference is
[`knowledge/SCHEMA.md`](https://github.com/x-haose/x-iztro/blob/main/knowledge/SCHEMA.md) in the
repository.

```rust
use x_iztro::{KnowledgePack, Language, StarKey};

let pack = KnowledgePack::builtin(Language::ZhCN).expect("zh-CN has a builtin pack");
let intro = pack.star_intro(StarKey::ZiweiMaj);
```

`KnowledgePack` is re-exported at the crate root; the other types live in `x_iztro::knowledge`.

## Types

### KnowledgePack

All fields are public and directly readable and writable. The map fields are `BTreeMap`, so
iteration order is stable and sorted by key.

| Field | Type | Meaning |
| --- | --- | --- |
| `schema` | `u32` | Format version, currently `SCHEMA_VERSION` (1) |
| `id` | `String` | Pack identifier; `"iztro-docs"` for the default pack |
| `version` | `String` | Pack version; for the default pack, retrieval date + short source commit |
| `language` | `String` | Language code of the texts, e.g. `"zh-CN"` |
| `extends` | `Option<String>` | The pack this overlay overlays; `None` for a standalone pack |
| `source` | `Source` | Origin and licence |
| `stars` | `BTreeMap<String, StarEntry>` | Star entries, keyed by `StarKey::as_key` |
| `patterns` | `BTreeMap<String, PatternEntry>` | Pattern entries, keyed by `PatternKey::as_key` |
| `palaces` | `BTreeMap<String, TextEntry>` | Palace entries, keyed by `Palace::as_key` |
| `mutagens` | `BTreeMap<String, TextEntry>` | Transformation entries, keyed by `Mutagen::as_key` |
| `concepts` | `BTreeMap<String, ConceptEntry>` | Glossary entries, keyed by slug |
| `topics` | `BTreeMap<String, TopicEntry>` | Reading topics, keyed by slug |

Implements `Clone`, `Default`, `PartialEq`, `Eq`, `Debug`, `Serialize`, `Deserialize`.

### Source

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | `Option<String>` | Source name |
| `url` | `Option<String>` | Source URL |
| `commit` | `Option<String>` | Source revision (git commit) |
| `license` | `Option<String>` | Licence |
| `author` | `Option<String>` | Author |
| `retrieved_at` | `Option<String>` | Retrieval date |
| `adapted` | `Option<String>` | Adaptation note: how the text was edited relative to the source |

### StarEntry

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | `Option<String>` | Display name in this pack's language |
| `category` | `Option<String>` | `"major"` / `"minor"` / `"adjective"` / `"dec"` / `"flow"` (a flowing star, a cross-reference entry pointing at its natal minor-star counterpart) |
| `group` | `Option<String>` | Grouping: the adjective star's category, the decorative star's group |
| `attributes` | `StarAttributes` | School attributes; all `None` when absent |
| `intro` | `Option<String>` | Reading (Markdown) |
| `summary` | `Option<String>` | Summary of the reading; absent when the reading is no wider than `SUMMARY_FALLBACK_WIDTH` |
| `combinations` | `BTreeMap<String, String>` | Reading for sharing a palace with another major star, keyed by that star |
| `combination_summaries` | `BTreeMap<String, String>` | Summaries of the pairing readings, keyed like `combinations` |

### StarAttributes

Every field is `Option<String>`, except `aliases` which is `Option<Vec<String>>`: `yin_yang`
(`yin` / `yang`), `five_elements` (`wood` / `fire` / `earth` / `metal` / `water`), `stem`
(`jia`…`gui`), `five_elements_note`, `dipper`, `chemistry`, `career`, `duty`, `aliases`,
`element_color`, `energy_color`.

<Callout type="info">
`five_elements` and `yin_yang` here are what the pack's source says, and may differ from the core
[`StarInfo`](/en/docs/rust/data), which is value-for-value identical to iztro's. The reason is in
the [guide](/en/docs/guide/guides/knowledge-pack#why-the-star-attributes-live-here).
</Callout>

### PatternEntry

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | `Option<String>` | Display name |
| `quotes` | `Option<Vec<String>>` | Classical quotations |
| `conditions` | `Option<String>` | The source's prose description of the conditions |
| `intro` | `Option<String>` | Reading |
| `summary` | `Option<String>` | Summary of the reading |

### TextEntry / ConceptEntry

`TextEntry` (palaces, transformations) has `name`, `intro` and `summary`; `ConceptEntry` (glossary) has `title`
and `intro`. All are `Option<String>`.

### TopicEntry

A reading topic: which palaces a kind of question looks at; [`topic_to_text`](/en/docs/rust/astro#topic_to_text)
selects palaces by it.

| Field | Type | Meaning |
| --- | --- | --- |
| `title` | `Option<String>` | Display name |
| `order` | `Option<u32>` | Display order, by which [`topics_in_order`](#star--pattern--palace--mutagen--topic--topics_in_order) sorts; `None` comes after every topic that has one |
| `surround` | `Option<Vec<String>>` | Palace keys taken with their trine & opposite, rendered in order |
| `palaces` | `Option<Vec<String>>` | Palace keys taken on their own (`bodyPalace` / `originalPalace` allowed), after the `surround` groups |
| `intro` | `Option<String>` | What the topic reads and why these palaces |
| `summary` | `Option<String>` | Summary of the intro |

`brief()` follows the same rule as [`StarEntry::brief`](#brief--combination_brief--missing_summaries).

### SCHEMA_VERSION

```rust
pub const SCHEMA_VERSION: u32 = 1;
```

The highest format version this library supports. Parsing a higher `schema` is an error.

### SUMMARY_FALLBACK_WIDTH

```rust
pub const SUMMARY_FALLBACK_WIDTH: usize = 240;
```

The summary layer's limit on a reading, in display width (CJK characters, kana, hangul and
full-width punctuation count 2, everything else 1; 120 Chinese characters). A reading within it is
used as is at the summary layer; an entry with a longer reading must carry a summary — see the
[guide](/en/docs/guide/guides/knowledge-pack#summaries).

## builtin

**Purpose**　Get the bundled default knowledge pack.

**Signature**

```rust
impl KnowledgePack {
    pub fn builtin(language: Language) -> Option<&'static KnowledgePack>
}
```

**Parameters**

| Parameter | Type | Meaning |
| --- | --- | --- |
| `language` | `Language` | Text language |

**Returns**　`Option<&'static KnowledgePack>` — `None` when there is no bundled pack for that
language. Only `Language::ZhCN` has one today. The pack is parsed once on first use and cached, so
later calls are a free static reference.

**Example**

```rust
let pack = KnowledgePack::builtin(Language::ZhCN).unwrap();
println!("{} {} {}", pack.id, pack.version, pack.stars.len());
println!("{:?}", pack.source.license);
println!("{}", KnowledgePack::builtin(Language::EnUS).is_some());
```

**Output**

```text
iztro-docs 2026-08-19+ec2d58b 162
Some("MIT")
false
```

## from_json / from_value

**Purpose**　Parse a pack from JSON text or from an already parsed `serde_json::Value`.

**Signature**

```rust
impl KnowledgePack {
    pub fn from_json(json: &str) -> Result<KnowledgePack, String>
    pub fn from_value(value: &serde_json::Value) -> Result<KnowledgePack, String>
}
```

`from_value` borrows the value tree without copying it, saving a serialisation round trip when you
already hold a `Value`; validation is the same as `from_json`.

**Returns**　`Result<KnowledgePack, String>`. Invalid JSON, or any error-level issue from [`check`](#check)
(missing `schema`, missing `id` / `version` / `language`, wrong field types, unknown keys, HTML in text and so on),
is an error whose message starts `invalid knowledge pack: ` and lists every error-level issue with its path.
Warning-level issues do not affect parsing.

<Callout type="info">
This returns `String` rather than [`IztroError`](/en/docs/rust/errors): a knowledge pack is data the
caller brings along, not input to a charting entry point. The bindings wrap it into each language's
`invalid_argument` error.
</Callout>

**Example**

```rust
let pack = KnowledgePack::from_json(r#"{
    "schema": 1, "id": "mine", "version": "1", "language": "zh-CN",
    "stars": {"ziweiMaj": {"intro": "我的紫微"}}
}"#)?;
println!("{:?}", pack.star_intro(StarKey::ZiweiMaj));
println!("{:?}", KnowledgePack::from_json(r#"{"schema": 99, "id": "x", "version": "1", "language": "zh-CN"}"#));
println!("{:?}", KnowledgePack::from_json(r#"{"schema": 1, "id": "x", "version": "1", "language": "zh-CN", "stars": {"ziweiMjj": {}}}"#));
```

**Output**

```text
Some("我的紫微")
Err("invalid knowledge pack: schema: knowledge pack schema 99 is newer than supported 1")
Err("invalid knowledge pack: stars.ziweiMjj: unknown key 'ziweiMjj' (did you mean 'ziweiMaj'?)")
```

**Edges and traps**

<Accordions>
<Accordion title="Absent and null mean the same thing">
Every entry and field is optional. A map field (`source`, `stars`, `combinations` …) written as
`null` is the same as leaving it out — Go serializes a nil map as `null`, and this keeps the default
serialization of every language mutually parseable.
</Accordion>
<Accordion title="Fields outside the spec are dropped">
A field the spec does not define, at the top level or in an entry (say `intor` for `intro`), is not rejected and
is gone after parsing; `check` reports it as a warning.
</Accordion>
</Accordions>

## check

**Purpose**　Check a pack's JSON value issue by issue, returning every issue at once. The rules, levels and all
issue codes are in [Knowledge packs · Checking a pack](/en/docs/guide/guides/knowledge-pack#checking-a-pack).

**Signature**

```rust
impl KnowledgePack {
    pub fn check(raw: &serde_json::Value, base: Option<&KnowledgePack>) -> Vec<KnowledgeIssue>
}

// x_iztro::knowledge
pub fn check(raw: &serde_json::Value, base: Option<&KnowledgePack>) -> Vec<KnowledgeIssue>
pub fn check_json(json: &str, base: Option<&KnowledgePack>) -> Vec<KnowledgeIssue>

pub struct KnowledgeIssue {
    pub level: IssueLevel,              // Error / Warning
    pub path: Vec<PathSegment>,         // Key(String) / Index(usize)
    pub code: IssueCode,                // as_key() is the snake_case code, e.g. "unknown_key"
    pub params: serde_json::Map<String, serde_json::Value>,
}
```

`check_json` takes JSON text and returns a single `invalid_json` issue when it does not parse. `base` is the pack it
will be merged onto; with it, base-relative reminders are reported too and the summary rules judge the merged entry.
`KnowledgeIssue` implements `Display` (`path: English description`); `message()` gives just the description and
`path_string()` the dotted path; `IssueCode::level()` is the fixed level of each code.

**Example**

```rust
let raw: serde_json::Value = serde_json::from_str(r#"{"schema": 1, "id": "my-school", "version": "1", "language": "zh-CN", "extends": "iztro-docs",
    "stars": {"ziweiMjj": {"intro": "本门认为……"}, "tianjiMaj": {"intor": "……"}}}"#)?;
let base = KnowledgePack::builtin(Language::ZhCN).unwrap();
for issue in KnowledgePack::check(&raw, Some(base)) {
    println!("{} {issue}", issue.level.as_key());
}
```

**Output**

```text
warning stars.tianjiMaj.intor: unknown field, dropped when parsed (did you mean 'intro'?)
error stars.ziweiMjj: unknown key 'ziweiMjj' (did you mean 'ziweiMaj'?)
```

## to_json

**Purpose**　Serialize to JSON (compact, no indentation).

**Signature**

```rust
impl KnowledgePack {
    pub fn to_json(&self) -> String
}
```

**Returns**　`String`. Optional fields that are `None` and empty maps are omitted, so
`from_json(&pack.to_json())` equals the original pack. For indented output use

## merged

**Purpose**　Layer overlay packs onto this one and return a new pack.

**Signature**

```rust
impl KnowledgePack {
    pub fn merged(&self, overlays: &[&KnowledgePack]) -> KnowledgePack
}
```

**Parameters**

| Parameter | Type | Meaning |
| --- | --- | --- |
| `overlays` | `&[&KnowledgePack]` | Overlays applied in slice order; later ones win |

**Returns**　A `KnowledgePack`; neither this pack nor the overlays change. The rules are in the
[guide](/en/docs/guide/guides/knowledge-pack#merge-rules): section by section, key by key, an
overlay's non-`None` fields replace the same-keyed entry's fields, `attributes` and `combinations`
merge field by field, array fields are replaced wholesale; when an overlay entry replaces a reading
without the matching summary, the base's old summary is dropped.

**Example**

```rust
let base = KnowledgePack::builtin(Language::ZhCN).unwrap();
let overlay = KnowledgePack::from_json(r#"{
    "schema": 1, "id": "my-school", "version": "1", "language": "zh-CN", "extends": "iztro-docs",
    "stars": {"ziweiMaj": {"intro": "我的紫微", "attributes": {"aliases": ["帝座"]}}},
    "patterns": {"zi_fu_tong_gong": {"intro": "我的紫府同宫"}}
}"#)?;
let pack = base.merged(&[&overlay]);

let ziwei = pack.star(StarKey::ZiweiMaj).unwrap();
println!("{:?} {:?} {:?}", ziwei.name, ziwei.attributes.aliases, ziwei.attributes.chemistry);
println!("{:?}", pack.pattern_intro(PatternKey::ZiFuTongGong));
println!("{:?}", pack.pattern(PatternKey::ZiFuTongGong).unwrap().quotes);
println!("{} {:?}", pack.id, base.star_intro(StarKey::ZiweiMaj).map(|s| s.chars().take(5).collect::<String>()));
```

**Output**

```text
Some("紫微") Some(["帝座"]) Some("尊贵")
Some("我的紫府同宫")
Some(["紫府同宫终身福厚。"])
my-school Some("紫微星号称")
```

## merge

**Purpose**　Merge one overlay into this pack in place.

**Signature**

```rust
impl KnowledgePack {

}
```

`merged` is the non-mutating version (clone, then `merge` each overlay). Use `merge` when you

## star / pattern / palace / mutagen / topic / topics_in_order

**Purpose**　Look up an entry by language-independent key (a topic by slug); list every topic in
display order.

**Signature**

```rust
impl KnowledgePack {
    pub fn star(&self, key: StarKey) -> Option<&StarEntry>
    pub fn pattern(&self, key: PatternKey) -> Option<&PatternEntry>
    pub fn palace(&self, palace: Palace) -> Option<&TextEntry>
    pub fn mutagen(&self, mutagen: Mutagen) -> Option<&TextEntry>
    pub fn topic(&self, slug: &str) -> Option<&TopicEntry>
    pub fn topics_in_order(&self) -> Vec<(&str, &TopicEntry)>
}
```

**Returns**　`None` when the pack has no such entry. The first four look the key up in the corresponding
`BTreeMap` by `as_key()`, exactly as `pack.stars.get(key.as_key())` would; the glossary has no
dedicated method, use `pack.concepts.get(slug)`.
`topics_in_order` returns every topic's slug and entry in display order: ascending `order`, topics
without one last, ties and topics without one by slug. Iterating `pack.topics` directly gives slug
order, not display order.

**Example**

```rust
let pack = KnowledgePack::builtin(Language::ZhCN).unwrap();
let ziwei = pack.star(StarKey::ZiweiMaj).unwrap();

println!("{:?} {:?} {:?}", ziwei.name, ziwei.category, ziwei.attributes.dipper);
println!("{:?}", ziwei.combinations.keys().collect::<Vec<_>>());
println!("{:?}", pack.palace(Palace::Soul).and_then(|e| e.name.clone()));
println!("{:?}", pack.mutagen(Mutagen::Lu).and_then(|e| e.name.clone()));
println!("{:?}", pack.concepts.get("tong-gong").and_then(|e| e.title.clone()));
```

**Output**

```text
Some("紫微") Some("major") Some("中天星系")
["pojunMaj", "qishaMaj", "tanlangMaj", "tianfuMaj", "tianxiangMaj"]
Some("命宫")
Some("化禄")
Some("遇、加、逢、同宫、同度")
```

## star_intro / pattern_intro

**Purpose**　Get the reading directly, skipping one layer of `Option`.

**Signature**

```rust
impl KnowledgePack {
    pub fn star_intro(&self, key: StarKey) -> Option<&str>
    pub fn pattern_intro(&self, key: PatternKey) -> Option<&str>
}
```

**Returns**　`None` both when the entry is missing and when it exists without a reading.

**Example**　List the natal patterns with their readings:

```rust
let pack = KnowledgePack::builtin(Language::ZhCN).unwrap();
let chart = by_solar("2000-8-16", 2, Gender::Female, true, Language::ZhCN, Config::default())?;

for hit in chart.patterns() {
    let intro = pack.pattern_intro(hit.key).unwrap_or("(not written in this pack)");

}
```

**Output**

```text
府相朝垣 “食禄千锺”的断语使
```

## brief / combination_brief / missing_summaries

**Purpose**　Pick material by the summary-layer rule, and check whether a pack can serve the summary
layer.

**Signature**

```rust
impl StarEntry {
    pub fn brief(&self) -> Option<&str>
    pub fn combination_brief(&self, other: &str) -> Option<&str>
}
impl PatternEntry {
    pub fn brief(&self) -> Option<&str>
}
impl TextEntry {
    pub fn brief(&self) -> Option<&str>
}
impl KnowledgePack {
    pub fn missing_summaries(&self) -> Vec<String>
}
```

**Returns**　`brief` gives the summary when there is one, otherwise the reading itself when it is no
wider than `SUMMARY_FALLBACK_WIDTH`, and `None` for a long reading without a summary;
`combination_brief` does the same for the pairing with `other` (the partner's star key). Once a pack
passes `missing_summaries` (an empty list), `None` only means there is no reading.
`missing_summaries` lists the paths of entries whose reading exceeds the limit without a summary,
such as `stars.ziweiMaj`, `stars.ziweiMaj.combinations.tianfuMaj` or `patterns.zi_fu_tong_gong`,
sorted by section and key; glossary entries never reach the text and are not checked.

**Example**

```rust
let pack = KnowledgePack::builtin(Language::ZhCN).unwrap();
let ziwei = pack.star(StarKey::ZiweiMaj).unwrap();
println!("{}", ziwei.brief().unwrap());
println!("{}", pack.star(StarKey::Hongluan).unwrap().brief().unwrap());
println!("{:?}", pack.missing_summaries());
```

**Output**

```text
帝王星，有王者特质：控制欲强、重体面、好为人师、大局观强；得资源能控场规划，否则眼高手低，忌被捧杀。
红鸾星会增加亲切感，同时会比较含蓄，看起来给人一种比较端庄、温柔贤淑的感觉。不过这只是一种观感，实际如何须结合主星和辅星一起判断。
[]
```

Hongluan's reading is within the limit, so the summary layer uses it as is.

## for_astrolabe / for_horoscope

**Purpose**　Pick by chart: cut a sub-pack holding only the entries relevant to this chart.

**Signature**

```rust
impl KnowledgePack {
    pub fn for_astrolabe(&self, chart: &Astrolabe) -> KnowledgePack
    pub fn for_astrolabe_with(&self, chart: &Astrolabe, config: &PatternConfig) -> KnowledgePack
    pub fn for_horoscope(&self, horoscope: &HoroscopeRef) -> KnowledgePack
    pub fn for_horoscope_with(&self, horoscope: &HoroscopeRef, config: &PatternConfig) -> KnowledgePack
}
```

**Parameters**

| Parameter | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `chart` | `&Astrolabe` | `for_astrolabe*` | — | The chart to select by; a re-anchored chart selects by its re-anchored layout |
| `horoscope` | `&HoroscopeRef` | `for_horoscope*` | — | The horoscope, with its chart and [query precision](/en/docs/rust/horoscope#precision) |
| `config` | `&PatternConfig` | `_with` only | — | Pattern criteria; the two without `_with` use `PatternConfig::default()` |

**Returns**　A standard `KnowledgePack` with the metadata carried over: `stars` holds the stars on
the chart (major, minor, adjective and the four groups of twelve gods; the 14 major stars'
`combinations` keep only partners that actually share the palace), `patterns` the hits under the
`config` criteria, `mutagens` all four entries, `palaces` and `concepts` empty. `for_horoscope` /
`for_horoscope_with` add the flowing stars and the patterns hit from each perspective from the decadal
scope down to the query precision; for a horoscope of a year or a month, the finer scopes belong to a
representative day the kernel picked and are left out.
Pair the sub-pack with [`patterns_with`](/en/docs/rust/patterns#patterns_with) /
`patterns_to_text_with` under the same criteria: different criteria hit different sets, and the
readings would then miss or over-include entries.
The selection rule is on [Picking by chart](/en/docs/guide/guides/knowledge-pack#picking-by-chart).

**Example**

```rust
let pack = KnowledgePack::builtin(Language::ZhCN).unwrap();
let chart = by_solar("2000-8-16", 2, Gender::Female, true, Language::ZhCN, Config::default())?;

let sub = pack.for_astrolabe(&chart);
println!("{} {} {} {}", sub.stars.len(), sub.patterns.len(), sub.mutagens.len(), sub.palaces.len());
println!("{:?}", sub.star(StarKey::WuquMaj).unwrap().combinations.keys().collect::<Vec<_>>());

let h = chart.horoscope("2025-1-1", 0)?;
let sub = pack.for_horoscope(&h);
println!("{} {}", sub.stars.len(), sub.patterns.len());

let year = chart.horoscope_of_year(2027)?;
let sub = pack.for_horoscope(&year);   // yearly at most
```

**Output**

```text
108 1 4 0
["tianxiangMaj"]
158 16
```

Wuqu shares its palace with Tianxiang on this chart, so Wuqu's `combinations` in the sub-pack keeps
only the Tianxiang entry.
