---
title: Calendar
description: Months of a lunar year, Gregorian ↔ lunar conversion, and the stem-branch of a lunar year — on the same calendar core as charting.
---

Calendar lookups without casting a chart: which months a lunar year has, how long each is and which one is
leap, Gregorian ↔ lunar conversion, and the stem-branch of a lunar year. They run on the same calendar core as
charting (a function-by-function port of lunar-typescript), so they agree day for day with the chart's
`rawDates.lunarDate` and year pillar; golden data generated by lunar-typescript checks every day of lunar years 1–9999.

Years 1–9999 are supported, Gregorian and lunar alike. Dates before 1582-10-15 are Julian, and 1582-10-05 to
10-14 do not exist.

<Callout title="Errors">
The conversions that take a full date (`calendar.solarToLunar`, `calendar.lunarToSolar`) return `IztroError` (code `invalid_date`) for a date that does
not exist, like the charting entry points; the lookups that take only a year (`calendar.lunarMonths`,
`calendar.lunarYearPillar`) return `IztroError` (code `invalid_argument`) for a year out of range, like horoscopes by lunar year.
</Callout>

```js
import { calendar } from 'x-iztro';
```

---

## calendar.lunarMonths

**Purpose**　Every month of a lunar year: its number, whether it is leap, its length, and the Gregorian date of
its first day.

**Signature**

```ts
calendar.lunarMonths(year: number): LunarMonthInfo[]
```

**Parameters**

| Parameter | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `year` | `number` | Yes | — | Lunar year, 1–9999 |

**Returns**　`LunarMonthInfo[]` in calendar order; a leap month directly follows the month it repeats. Each item:

| Field | Type | Description |
| --- | --- | --- |
| `month` | `number` | Month 1–12; a leap month carries the number it repeats, so leap 4th month is 4 |
| `isLeap` | `boolean` | Whether the month is leap |
| `dayCount` | `number` | Length: 29 (short month) or 30 (long month) |
| `firstDay` | `RawSolarDate` | Gregorian date of the first day: `solarYear`, `solarMonth`, `solarDay` |

**Example**　2023 has a leap second month:

```js
for (const m of calendar.lunarMonths(2023).slice(0, 4)) {
  const d = m.firstDay;
  console.log(m.month, m.isLeap, m.dayCount, `${d.solarYear}-${d.solarMonth}-${d.solarDay}`);
}
```

**Output**

```text
1 false 29 2023-1-22
2 false 30 2023-2-20
2 true 29 2023-3-22
3 false 29 2023-4-20
```

**Edge cases**

<Accordions>
<Accordion title="Not always 12 or 13 months">
A few ancient years, matching lunar-typescript, are a month short: lunar year 237 has 11 months and no third
month. When iterating months, go by the returned list rather than looping 1–12.
</Accordion>
<Accordion title="The last 27 days of lunar year 9999 fall in Gregorian 10000">
The 12th month of lunar year 9999 begins on 9999-12-30; every month's first day is within Gregorian 9999, so
`firstDay.solarYear` is never 10000. Days 3 to 29 of that month — 27 days — fall in Gregorian year 10000, and
`calendar.lunarToSolar` returns `solarYear` 10000 for them. Those days cannot be passed on to entry points that take a
Gregorian year 1–9999 (charting, `calendar.solarToLunar`).
</Accordion>
</Accordions>

## calendar.solarToLunar

**Purpose**　Convert a Gregorian date to the lunar calendar.

**Signature**

```ts
calendar.solarToLunar(year: number, month: number, day: number): RawLunarDate
```

**Parameters**

| Parameter | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `year` | `number` | Yes | — | Gregorian year, 1–9999 |
| `month` | `number` | Yes | — | Gregorian month, 1–12 |
| `day` | `number` | Yes | — | Gregorian day |

**Returns**　`RawLunarDate`: `lunarYear`, `lunarMonth` (1–12), `lunarDay`, `isLeap` — the same type as the
chart's `rawDates.lunarDate`.

**Example**　2023-3-22 is the first day of the leap second month:

```js
const l = calendar.solarToLunar(2023, 3, 22);
console.log(l.lunarYear, l.lunarMonth, l.lunarDay, l.isLeap);
```

**Output**

```text
2023 2 1 true
```

**Edge cases**

<Accordions>
<Accordion title="Early January of year 1 is lunar year 0">
The first few dozen days of Gregorian year 1 are still in the 11th and 12th months of lunar year 0, so
`lunarYear` is 0; that 0 cannot be passed back to lunar inputs, which accept 1–9999.
</Accordion>
<Accordion title="The calendar reform gap">
1582-10-05 to 10-14 do not exist (the day after Julian 4 October is Gregorian 15 October); passing one returns
`IztroError` (code `invalid_date`).
</Accordion>
</Accordions>

## calendar.lunarToSolar

**Purpose**　Convert a lunar date to the Gregorian calendar.

**Signature**

```ts
calendar.lunarToSolar(
  year: number,
  month: number,
  day: number,
  options?: { isLeap?: boolean },
): RawSolarDate
```

**Parameters**

| Parameter | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `year` | `number` | Yes | — | Lunar year, 1–9999 |
| `month` | `number` | Yes | — | Lunar month, 1–12; for a leap month, the number it repeats |
| `day` | `number` | Yes | — | Lunar day, within the month's length |
| `options.isLeap` | `boolean` | No | `false` | The day is in the leap month |

**Returns**　`RawSolarDate`: `solarYear`, `solarMonth`, `solarDay`.

**Example**

```js
const s = calendar.lunarToSolar(2023, 2, 1, { isLeap: true });
console.log(`${s.solarYear}-${s.solarMonth}-${s.solarDay}`);

// 2024 has no leap second month: an error, not the regular second month
try {
  calendar.lunarToSolar(2024, 2, 1, { isLeap: true });
} catch (e) {
  console.log(e.code);
}
```

**Output**

```text
2023-3-22
invalid_date
```

**Edge cases**

<Accordions>
<Accordion title="No such leap month is an error">
When `options.isLeap` is true but the year does not repeat that month, the result is `IztroError` (code `invalid_date`). The charting entry
point (`astro.byLunar` with `isLeapMonth`, as in iztro) ignores the leap flag in that case and charts the regular month; the
calendar conversion does not, because falling back to the regular month gives a date a month off that looks
perfectly valid.
</Accordion>
<Accordion title="No fix_leap">
Charting's `fixLeap` (days after the 15th of a leap month count as the next month) decides which month the
stars are placed by; it does not change which Gregorian day a date is, so the only parameter here is whether
the month is leap.
</Accordion>
</Accordions>

## calendar.lunarYearPillar

**Purpose**　The stem-branch of a lunar year, as language-independent stem and branch keys.

**Signature**

```ts
calendar.lunarYearPillar(year: number): Pillar
```

**Parameters**

| Parameter | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `year` | `number` | Yes | — | Year number, 1–9999 |

**Returns**　`Pillar` (`[stem key, branch key]`). Year 4 is jia-zi, and the cycle runs on by year number from there.

**Example**

```js
const [stem, branch] = calendar.lunarYearPillar(2024);
console.log(stem, branch);
```

**Output**

```text
jiaHeavenly chenEarthly
```

**Year boundary**　The stem-branch depends only on the year number, not on `year_divide`; the boundary setting
decides from which day that pillar applies. The chart's year pillar (`rawDates.chineseDate.pillarKeys()[0]`) takes the pillar of the
year number given by this table:

| Setting | Days the stem-branch of year number N covers |
| --- | --- |
| Lunar New Year (`yearDivide: 'normal'`, default) | Lunar year N, from New Year's Day to New Year's Eve |
| Start of spring (`yearDivide: 'exact'`) | From the start of spring (lichun) in Gregorian year N to the day before the next one |

Take 2024: the start of spring falls on 2-4 and Lunar New Year on 2-10. The days 2-4 to 2-9 belong to gui-mao
(lunar 2023) under the New Year boundary and to jia-chen (year number 2024) under the start-of-spring boundary.
To get the year pillar for a date, settle the year number by the boundary first, then take its pillar.
