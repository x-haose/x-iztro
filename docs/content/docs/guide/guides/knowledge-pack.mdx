*适合：要在排盘结果之上给出文字解读的人*

排完盘拿到的是事实：命宫在午、武曲在财帛且化权、这张盘成了府相朝垣。
接下来要回答的「武曲是什么意思」「府相朝垣好在哪里」不是事实，是**观点**——
不同门派、不同书、不同老师给的答案不一样。

x-iztro 把这两件事分开：内核只做事实判定（排盘、运限、格局），
解读文本与星耀的门派属性放在**知识包**里。知识包是一份 JSON，
协议是「语言无关标识 → 文本与属性」。库里内嵌一份默认包，开箱即用；
不认同其中的说法，写一份覆盖包逐条改掉。包是 to_text 家族的参数：传给
[带释义的文本](/zh/docs/guide/guides/to-text#带释义的文本)，释义就按盘取材内联在事实旁——
每宫事实后跟该宫星耀释义，格局列表后跟格局释义，文末附四化释义。

## 内核与知识包的分工

| | 内核 | 知识包 |
| --- | --- | --- |
| 内容 | 十二宫、星耀落宫、亮度、四化、运限、格局命中 | 星耀解读、格局解读、宫位与四化含义、术语、星耀的门派属性 |
| 性质 | 事实，可与 iztro 逐字段对照 | 观点，换一家说法就换一份 |
| 出错的样子 | 盘排错了 | 解读你不认同 |
| 怎么改 | 不能改（改了就不是这套算法） | 换包或写覆盖包 |

两边的接缝就是**语言无关标识**：星耀用 `ziweiMaj`、格局用 `zi_fu_tong_gong`、
宫位用 `soulPalace`、四化用 `sihuaLu`。内核输出的每个字段都带这些标识
（见[标识体系](/zh/docs/guide/guides/keys)），拿它去知识包里取文本即可，
不必匹配译名，也不受盘面语言影响。

## 内嵌的默认包里有什么

| 段 | 条目数 | 内容 |
| --- | --- | --- |
| `stars` | 164 | 主星 14、辅星 14、杂耀 40、神煞 46、流耀 50——全部 `StarKey` 都有条目。主辅杂神各带卡片属性（阴阳、五行、斗分、化气、职业、职务、别号、五行色、能量色）与特性正文；14 颗主星另有与其他主星的双星组合解读；流耀条目（`category: "flow"`）是指向对应本命辅星的对照性条目，机器可读对照表由 `flow_star_counterparts`（Go `FlowStarCounterparts`）提供 |
| `patterns` | 64 | 每条带古籍引文、成立条件的文字描述与解读正文 |
| `palaces` | 12 | 十二宫各自的含义 |
| `mutagens` | 4 | 禄权科忌各自的含义 |
| `concepts` | 51 | 术语与基础概念（同宫、本宫、身宫、地支六合、三方四正、飞星四化、亮度…） |
| `topics` | 13 | 解读主题：每类问题看哪些宫，见[主题](#主题) |

释义正文取自 [iztro-docs](https://github.com/SylarLong/iztro-docs) 的《学习》各页
（MIT License，作者 Sylar Long），锁定来源 commit（`source.commit`），文本经 x-iztro 整理改写为第三人称释义口吻（`source.adapted` 注明），
包的 `source` 段完整记录来源、commit、许可与作者。文本字段是 Markdown。
正文较长的 134 条（主辅星 28、双星组合 48、格局 43、宫位 11、四化 4）另有不超过 50 字的[摘要](#摘要)。

<Callout type="warn" title="默认包目前只有 zh-CN">
其他五种语言没有内嵌默认包：Rust 的 `KnowledgePack::builtin` 返回 `None`，
Python、Go、JavaScript 报 `invalid_argument`。要别的语言，自己写一份包，
或者把中文条目连同盘一起交给大模型，让它边译边解读。
</Callout>

<Callout type="info">
默认包让 Go 侧内嵌的 wasm 增大了约 380 KB。Rust 与 Python 侧同样内嵌这份数据。
</Callout>

## 摘要

正文可以配一段摘要：`intro` 配 `summary`，`combinations` 里的每一条配 `combinationSummaries` 里同键的一条。
带释义的 to_text 在摘要层用摘要代替正文，一张盘的释义从两万字量级降到几千字。

- 长度按显示宽度计：汉字、假名、谚文与全角标点计 2，其余字符计 1；
- 正文宽度不超过 240（中文 120 字）的条目，正文本身就是摘要的长度，摘要层直接用正文，不另写摘要；
- 正文更长的条目要写摘要：单段，宽度不超过 100（中文 50 字），只压缩原文，不增减内容；
- 格局的成立条件（`conditions`）不进摘要层。

包里只要有一条「正文超过 240 却没有摘要」，请求摘要层就报错并列出全部缺项，不截断、也不改用全文。
自己写的包要支持摘要层，按这几条补齐即可。

## 主题

「婚恋看哪些宫」「财运看哪些宫」是论法，各家说法不一，所以主题也写在包里（`topics` 段），
内核只按定义选宫，生成[主题文本](/zh/docs/guide/guides/to-text#按主题取材)。一个主题有两组宫位：
`surround` 的宫连同各自的三方四正一起取，`palaces` 的宫只取本宫（可写 `bodyPalace`、`originalPalace`）。

```json
"topics": {
  "romance": {
    "title": "婚恋",
    "order": 50,
    "surround": ["spousePalace"],
    "palaces": ["soulPalace", "bodyPalace", "childrenPalace"],
    "intro": "看婚恋：夫妻宫是择偶观与对感情的态度，其三方四正（官禄、迁移、福德）一并会照；命宫看本人，身宫看后天的着力之处，子女宫是桃花宫位。"
  }
}
```

默认包的 13 个主题：

| `order` | slug | 主题 | 连三方四正 | 只取本宫 |
| --- | --- | --- | --- | --- |
| 10 | `overall` | 总论 | 命宫 | 身宫、福德 |
| 20 | `personality` | 性格 | — | 命宫、迁移、福德、身宫 |
| 30 | `career` | 事业 | 官禄 | — |
| 40 | `wealth` | 财运 | 财帛 | 田宅 |
| 50 | `romance` | 婚恋 | 夫妻 | 命宫、身宫、子女 |
| 60 | `health` | 健康 | 疾厄 | 命宫 |
| 70 | `parents` | 父母 | 父母 | 兄弟、命宫 |
| 80 | `children` | 子女 | 子女 | 命宫 |
| 90 | `siblings` | 兄弟 | 兄弟 | 命宫 |
| 100 | `friends` | 交友 | 仆役 | 命宫 |
| 110 | `property` | 田宅 | 田宅 | 财帛 |
| 120 | `travel` | 迁移 | 迁移 | — |
| 130 | `spirit` | 精神 | 福德 | 命宫、身宫 |

选宫依据默认包宫位条目的释义：财富的积累看田宅宫、与母亲的相处看兄弟宫、桃花看子女宫。
主题按本命盘的宫位取材，运限问题用运限文本。不同意某个主题的取宫，用覆盖包整组改写
`surround` / `palaces`（数组整体替换），或者新增自己的主题。

主题的显示顺序由 `order` 定：按 `order` 升序，没有 `order` 的排在最后，相同或都没有时按 slug；键在 JSON 里的书写顺序不算数。
列出全部主题的接口按这个顺序返回：Rust `topics_in_order`、Python 与 TypeScript `topics()`、Go `TopicSlugs`。
默认包以 10 为步长编号，覆盖包给新主题写 `"order": 35` 就排在事业与财运之间，也可以只改某个主题的 `order` 挪动它。

## 按盘取材

整包 164 颗星、64 条格局，一张盘用不到这么多。`for_astrolabe` 从包里裁出只含这张盘的子包，
`for_horoscope` 在此之上再加运限层的材料：

| 段 | `for_astrolabe` | `for_horoscope` 另加 |
| --- | --- | --- |
| `stars` | 十二宫上出现的星：主星、辅星、杂耀与四组十二神；14 主星的 `combinations` 只保留对方主星确在同宫的那些 | 大限到查询精度各层的流耀 |
| `patterns` | 按格局口径命中的格局 | 大限到查询精度各层视角命中的格局 |
| `mutagens` | 禄权科忌四条，与盘无关 | — |
| `palaces` / `concepts` | 空——宫位与术语与盘无关，按需从整包直接查 | — |

运限层只取到运限目标的查询精度：按日期取的到流时，按农历年取的到流年，按农历月取的到流月——
比精度细的层级是内核挑的代表日的，不进子包。各语言都传运限对象，按它的精度取材。

格局口径可选传：Rust 走 `for_astrolabe_with(&chart, &PatternConfig)` /
`for_horoscope_with(&h, &PatternConfig)`（不带 `_with` 的两个即默认口径），
Python 是 `config=` 关键字，Go 是第二个参数 `*PatternConfig`（`nil` 即默认）。
子包要和 `patterns` / `patterns_to_text` 配同一口径：口径不同，命中集合不同，释义就会缺项或多项。
Go 另有 `BuiltinKnowledge().ForAstrolabe(chart, nil)` 这条路，让内核直接读内嵌包，不必先取整包再送回。

返回的仍是标准知识包（元信息沿用本包），可以继续合并、序列化、按 key 查，
或者反过来作为 to_text 的释义参数。2000-8-16 寅时 女这张盘从默认包取出的子包：
本命 108 星 / 1 格局 / 4 四化，序列化约 75 KB（整包约 219 KB）；
2025-1-1 的运限再加流耀与各层格局，158 星 / 16 格局。

## 写一份覆盖包

覆盖包是同样格式的 JSON，只写要改的条目与字段，`extends` 记被覆盖包的 `id`。
下面这份改掉紫微的解读与别号、换掉紫府同宫的解读，其余原样保留：

```json
{
  "schema": 1,
  "id": "my-school",
  "version": "2026-08-19",
  "language": "zh-CN",
  "extends": "iztro-docs",
  "stars": {
    "ziweiMaj": {
      "intro": "紫微在我这一派看来先看格局高低，再论性情。",
      "attributes": { "aliases": ["帝座"] }
    }
  },
  "patterns": {
    "zi_fu_tong_gong": { "intro": "紫府同宫，我只把它当作起点高，不当作福厚。" }
  }
}
```

合并出一份新包：

<Tab value="Rust">

每条问题的字段：

| 字段 | 说明 |
| --- | --- |
| `level` | `error` 或 `warning`，见下 |
| `path` | JSON 路径：对象键为字符串、数组下标为数字；空路径指包本身 |
| `code` | 问题种类，见下表 |
| `params` | 补充数据，键随 `code` 而定；`suggestion` 是最接近的已知标识，见下文 |
| `message` | 带点分路径的英文说明，供日志；界面请按 `code` 与 `params` 组织文案 |

给了底包时，另报相对底包的提醒（空串覆盖底包的值、语言或 `extends` 与底包不符），
摘要规则按「合并到底包之后」的条目判断——覆盖包换了长正文却没给摘要，底包的旧摘要会在合并时失效，
因此同样报缺摘要。没给底包而包声明了 `extends` 时，只凭这一份判断不了正文与摘要是否成对、
主题取哪些宫，这两类不报。

### 级别与构造

- **error**：违反规范的「必须 / 不得」，或内核用到该处时会失败。构造知识包的入口（Rust `from_json` /
  `from_value`，Python `from_dict` / `from_json`，Go `ParseKnowledgePack`，JavaScript `fromObject` /
  `fromJSON`，以及 `merged` 收到的覆盖包对象）遇到 error 级问题即拒绝，报 `invalid_argument`，
  信息逐条列出全部 error 级问题；Python、JavaScript 的异常与 Go 的 `*Error` 另带 `issues`，即完整的问题列表。
- **warning**：「应 / 不应」、解析时被丢弃的字段、按字面匹配的启发式规则，以及相对底包的提醒。只报告，不拒绝。

### 问题种类

出处一栏的 § 指仓库里的 `knowledge/SCHEMA.md`；「默认包测试」指 `tests/knowledge_pack.rs` 对内嵌默认包的断言。
`suggestion?` 表示可能没有。

| code | 级别 | 含义 | 出处 | params |
| --- | --- | --- | --- | --- |
| `invalid_json` | error | 文本不是合法 JSON（只有收文本的入口会报） | §7 | `message` |
| `not_object` | error | 包或条目不是 JSON 对象 | §2 | — |
| `schema_missing` | error | `schema` 缺失、为 null 或 0 | §2、§7「缺失或为 0 的包必须被拒绝」 | — |
| `schema_unsupported` | error | `schema` 比本库支持的版本新 | §7 | `value`、`supported` |
| `wrong_type` | error | 字段类型不符 | §2、§4 各表的类型 | `expected` |
| `required_missing` | error | `id` / `version` / `language` 缺失或为空串 | §2「必须」 | — |
| `unknown_language` | error | `language` 不是 x-iztro 语言码 | §2 | `value`、`suggestion`? |
| `unknown_key` | error | 条目键（含双星组合的对方星）不是内核认识的标识 | §3；默认包测试逐段断言键合法 | `key`、`suggestion`? |

| `invalid_slug` | error | 术语或主题的 slug 含小写字母、数字、连字符以外的字符 | §4.4、§4.5 | `key` |
| `unknown_palace` | error | 主题的宫位不是宫位标识、`bodyPalace` 或 `originalPalace` | §4.5；生成主题文本即报错 | `value`、`suggestion`? |
| `html_in_text` | error | 正文含 HTML 标签或注释 | §5「不得使用 HTML 标签」 | `snippet` |

| `summary_not_needed` | warning | 正文宽度不超过 240 却另写了摘要 | §5.1「不应」另写摘要 | `width`、`limit` |

HTML、图片、站外链接与页面引用只查 SCHEMA §5 列出的正文类字段（各条目的 `intro`、`summary`、`conditions` 与两个组合映射的值），
行内代码（按 CommonMark：转义的反引号不作开头，不跨空行）里的内容不算；古籍引文 `quotes` 是逐字转录的纯文本，不查。内嵌默认包校验结果为空。

### 最接近的标识

`unknown_key`、`unknown_language`、`unknown_palace`、`invalid_value` 与 `unknown_field` 在找得到时给出
`suggestion`：先找只差大小写的候选（语言码还接受下划线写法，`zh_cn` 提示 `zh-CN`）；否则取编辑距离最小者。
距离按插入、删除、替换、相邻两字换位各计 1（换位是标识拼写最常见的手误，`ziwieMaj` 与 `ziweiMaj` 距离为 1），
上限为写错的词长度的三分之一（不足 3 个字符按 3 算），与 rustc 提示「找不到名字」时的阈值相同；
超过上限不给提示，免得把无关的词凑成建议。同距离取标识表里靠前的。

### 口吻红线只取一部分

默认包有一条口吻红线测试，禁止「读者」「大家肯定」「韭菜」「见上表」「点击」等写法。其中指向页面布局与站点功能的
那部分（「见上表」「下表中」「前面提到」「详见」「参见」「本站」「点击」等）落在规范 §5「不得依赖页面上下文」上，
对任何包都成立，`page_reference` 只查这部分，且是字面匹配，定为 warning。其余的口语与对话残留是默认包
「第三人称释义口吻」（§8）的写法要求，规范没有要求用户包采用，不查。

## 合并规则

以底包为底，逐段（`stars` / `patterns` / `palaces` / `mutagens` / `concepts` / `topics`）按键合并：

- 覆盖包里出现的条目，其**非 null 字段**覆盖底包同键条目的对应字段，未出现的字段保留
- `attributes` 与 `combinations` 同样按字段 / 子键合并
- 数组字段（`aliases`、`quotes`、主题的 `surround` / `palaces`）整体替换，不做逐项合并
- 底包没有的键直接新增
- 把某字段显式写成 `null` **不会删除**底包内容（缺省与 null 同义）；要删除请整包替换
- 唯一会删掉内容的情况：覆盖条目换了 `intro`（或某条组合解读）却没给对应的摘要，合并结果去掉底包的旧摘要——
  它描述的是被换掉的正文，留着会让摘要层说的是旧门派的话
- 合并后的 `id` / `version` / `language` / `source` 取覆盖包的（若非空），`extends` 保留底包的

`schema` 高于本库支持的版本直接报错，不做降级解析。

## 为什么星耀的阴阳五行放在这里

星耀的五行看起来像事实，其实也是观点。iztro 自带的 `starsInfo` 表与
iztro-docs 星耀卡片本身就对不上：

| 星 | iztro 的 `starsInfo` | iztro-docs 卡片 |
| --- | --- | --- |
| 贪狼 | 水 | 甲木（气为水） |
| 巨门 | 阴土 | 癸水、己土（藏金、木） |

同一位作者的两处数据都不一致，说明这类属性是门派说法而非唯一答案。
所以 x-iztro 的核心 `StarInfo` 保持与 iztro 逐值一致（迁移过来的代码不会变行为），
卡片上那套属性放进知识包，想换就换。
